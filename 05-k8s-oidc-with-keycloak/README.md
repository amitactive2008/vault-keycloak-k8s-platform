# Kubernetes SSO via Keycloak OIDC

Integrates `kubectl` authentication with the Keycloak `kind` realm so that
users log in with their Keycloak credentials instead of long-lived kubeconfig
certificates.

## How it works

```
kubectl / kubelogin
      │
      │  1. opens browser to https://keycloak.local
      ▼
 nginx ingress  ──TLS termination──►  Keycloak pod  (HTTP internally)
      │
      │  2. user logs in → Keycloak issues JWT
      │     iss: https://keycloak.local/realms/kind
      │     aud: kubernetes
      │     groups: [team-a]
      ▼
 kubelogin stores token in ~/.kube/cache/
      │
      │  3. kubectl sends token to API server
      ▼
 kube-apiserver
   --oidc-issuer-url=https://keycloak.local/realms/kind
   --oidc-client-id=kubernetes
   --oidc-username-claim=preferred_username
   --oidc-groups-claim=groups
   --oidc-ca-file=/etc/kubernetes/pki/keycloak-local-ca.crt
      │
      │  4. validates JWT, extracts username + groups
      ▼
 RBAC  →  allow / deny
```

**Key design points:**
- The kube-apiserver is inside the kind cluster and reaches Keycloak through
  the nginx ingress ClusterIP (port 443). The nginx pod TLS-terminates the
  request and sets `X-Forwarded-Proto: https`, so Keycloak issues tokens with
  an `https://` issuer.
- Vault OIDC is **not affected** — Vault pods use CoreDNS which resolves
  `keycloak.local` to the Keycloak ClusterIP directly (port 80 / HTTP). The
  two OIDC flows coexist independently.
- Kubernetes 1.30+ requires `https://` for `--oidc-issuer-url`. A self-signed
  CA is used; the CA cert is provided via `--oidc-ca-file` to the API server
  and via `--certificate-authority` to kubelogin.

## Access matrix

| Keycloak group | Cluster access    | Namespace access                |
|----------------|-------------------|---------------------------------|
| `devops`       | `cluster-admin`   | All namespaces (full admin)     |
| `team-a`       | —                 | `team-a` namespace only (admin) |
| `team-b`       | —                 | `team-b` namespace only (admin) |

## File structure

```
k8s-oidc/
├── setup.sh                  # end-to-end setup script
├── keycloak-local-ca.crt     # self-signed CA cert (generated by setup.sh)
├── kubeconfig-oidc.yaml      # kubeconfig snippet (generated by setup.sh)
└── rbac/
    ├── devops-cluster-admin.yaml   # ClusterRoleBinding: devops → cluster-admin
    ├── team-a.yaml                 # Namespace team-a + RoleBinding + ns-viewer
    └── team-b.yaml                 # Namespace team-b + RoleBinding + ns-viewer
```

## Tips

### Switching users — clear the OIDC token cache

All three kubeconfig users (`devops-oidc`, `team-a-oidc`, `team-b-oidc`) share
the **same cache key** because they use the same issuer URL and client ID.
If you switch context (e.g. from `team-a` → `devops`) without clearing the
cache, `kubectl oidc-login` will reuse the old user's token and the API server
will reject the request with a `Forbidden` error like:

```
Error from server (Forbidden): pods is forbidden: User "https://keycloak.local/realms/kind#team-a-user-1"
cannot list resource "pods" in API group "" in the namespace "default"
```

**Fix:** clear the cache before switching users, then re-run any `kubectl` command
to trigger a fresh browser login:

```bash
rm -f ~/.kube/cache/oidc-login/*
kubectl get pods   # opens browser → log in as the new user
```

## Running the setup script

```bash
cd keycloak/k8s-oidc/
chmod +x setup.sh
./setup.sh
```

The script is fully idempotent — safe to re-run. It:

1. Generates a self-signed CA + TLS cert for `keycloak.local`
2. Creates a TLS secret in the `keycloak` namespace and patches the ingress
3. Creates the `kubernetes` public OIDC client in Keycloak with:
   - groups mapper (`full.path=false` → `devops`, `team-a`, `team-b`)
   - audience mapper (`aud=kubernetes`)
4. Patches `/etc/kubernetes/manifests/kube-apiserver.yaml` on the control-plane
   and waits for the API server to restart
5. Applies the RBAC manifests
6. Writes `kubeconfig-oidc.yaml` and `keycloak-local-ca.crt`

> **Note for contributors:** `kubeconfig-oidc.yaml` and `keycloak-local-ca.crt`
> are **generated files** — they are listed in the root `.gitignore` and should
> never be committed. The kubeconfig contains absolute local paths that differ
> per machine. Run `setup.sh` to regenerate them.

## Getting cluster access (user setup)

### 1. Prerequisites

```bash
# kubelogin provides the oidc-login kubectl plugin
brew install int128/kubelogin/kubelogin

# Verify
kubectl oidc-login --version
```

### 2. Add keycloak.local to your /etc/hosts

```bash
sudo sh -c 'echo "127.0.0.1  keycloak.local" >> /etc/hosts'
```

> **macOS note:** macOS tries mDNS for `.local` domains before checking
> `/etc/hosts`, which can cause a DNS timeout in some tools. If you see
> connection timeouts, flush the DNS cache:
> ```bash
> sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
> ```

### 3. Trust the self-signed CA certificate

The Keycloak ingress uses a self-signed TLS certificate. Your browser and
kubelogin both need to trust the CA that signed it.

**macOS — add to system keychain (trusted by all apps including browsers):**

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain \
  keycloak/k8s-oidc/keycloak-local-ca.crt
```

After adding, restart your browser for the change to take effect.

> **One CA covers both services.** The same `keycloak-local-ca.crt` signs both
> `https://keycloak.local` and `https://vault-webui.local`. Trusting it once
> gives your browser a valid padlock for both.

> **Verify:** Open `https://keycloak.local` and `https://vault-webui.local` in
> your browser — both should show a valid padlock (no certificate warning).

### 4. Add the OIDC contexts to kubectl

The generated `kubeconfig-oidc.yaml` contains three contexts (`devops`,
`team-a`, `team-b`). Merge it with your existing kubeconfig:

```bash
export KUBECONFIG=~/.kube/config:$(pwd)/keycloak/k8s-oidc/kubeconfig-oidc.yaml
```

To make this permanent, add the line to your shell profile (`~/.zshrc` or
`~/.bashrc`) or merge the files:

```bash
kubectl config view --flatten > ~/.kube/config-merged
mv ~/.kube/config-merged ~/.kube/config
```

### 5. Log in and run commands

Switch to the context for your team, then run any kubectl command. On the
**first use**, kubelogin opens a browser tab for you to log in with your
Keycloak credentials. The token is cached locally and refreshed automatically.

#### team-a user

```bash
kubectl config use-context team-a

kubectl get pods -n team-a          # ✓ allowed
kubectl get pods -n team-b          # ✗ forbidden
kubectl get nodes                   # ✗ forbidden
```

#### team-b user

```bash
kubectl config use-context team-b

kubectl get pods -n team-b          # ✓ allowed
kubectl get pods -n team-a          # ✗ forbidden
```

#### devops user (cluster-admin)

```bash
kubectl config use-context devops

kubectl get nodes                   # ✓ all nodes
kubectl get pods -A                 # ✓ all namespaces
kubectl create namespace foo        # ✓ full admin
```

### 6. Log out / switch user

kubelogin caches tokens per issuer + client ID. To log out and switch to a
different Keycloak user:

```bash
# Clear kubelogin's token cache
rm -rf ~/.kube/cache/oidc-login/

# Next kubectl command will open the browser login page again
kubectl get pods -n team-a
```

## Troubleshooting

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| `error: You must be logged in (Unauthorized)` | Token has wrong `aud` or `iss` claim | Re-run `setup.sh` to ensure the audience mapper exists; verify the CA cert is trusted |
| Browser shows certificate warning on `https://keycloak.local` | CA cert not trusted by system | Run the `security add-trusted-cert` command in step 3 and restart the browser |
| DNS timeout resolving `keycloak.local` | macOS mDNS interference | Flush DNS cache: `sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder` |
| `dial tcp: lookup keycloak.local: no such host` | macOS Go resolver bypasses `/etc/hosts` for `.local` | `kubeconfig-oidc.yaml` already contains `GODEBUG=netdns=go`; ensure you are using the generated file from `setup.sh` |
| `pods is forbidden: User "..." cannot list resource "pods" in namespace "team-b"` | Working correctly | team-a users are intentionally denied access to team-b |
| `invalid_scope` error on browser redirect | `--oidc-extra-scope=groups` was set | Re-run `setup.sh` to regenerate `kubeconfig-oidc.yaml` without the invalid scope |
| API server not restarting after setup.sh | kubelet takes time to detect manifest change | Wait 60–120 s; check with `podman exec vault-control-plane crictl ps \| grep apiserver` |
| kubelogin browser does not open | `kubelogin` not installed or not in PATH | `brew install int128/kubelogin/kubelogin` |
| Lost token cache after machine restart | Tokens expire | Simply run a kubectl command — kubelogin re-authenticates automatically |

## What was NOT changed

- The existing Vault OIDC integration (`vault-integration/`) is unaffected.
  Vault uses `http://keycloak.local` (via CoreDNS → Keycloak ClusterIP), which
  continues to work independently of the HTTPS ingress path.
- Keycloak admin credentials and the `kind` realm are unchanged.
- No new ingress rules or host-level ports were added; port 443 was already
  mapped by the kind cluster config.
